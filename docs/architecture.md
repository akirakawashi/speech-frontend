# Архитектура speech-frontend

Решение владельца 12.10.2026: фронтенд раскладываем по Feature-Sliced Design
(FSD) целиком — шесть слоёв, срезы, сегменты и публичные API. Правила работы —
в [AGENTS.md](../AGENTS.md); здесь — что где лежит и почему.

## Раскладка проекта

```
app/            маршруты Next.js: только отдают страницу из src/pages
pages/          заглушка, чтобы Next не принял src/pages за Pages Router
src/
  app/          запуск приложения
  pages/        экраны
  widgets/      крупные блоки, общие для нескольких экранов
  features/     действия пользователя, общие для нескольких экранов
  entities/     понятия предметной области
  shared/       то, что не знает о предметной области
e2e/            сквозные прогоны Playwright против стенда
scripts/        проверки проекта
```

Импорт идёт только сверху вниз: `app → pages → widgets → features → entities →
shared`. Срезы одного слоя друг друга не импортируют.

## Почему маршруты лежат вне `src`

Next.js ищет каталоги `app` и `pages` сначала в корне, потом в `src`. У FSD
слои называются так же, а устроены иначе: в `src/pages` лежат срезы со своими
сегментами, а не файлы-маршруты.

Поэтому маршруты вынесены в корневой `app/`. Файл маршрута — одна строка:

```ts
export { QualityPage as default } from '@/pages/quality';
```

Корневой `pages/` нужен только для того, чтобы Next нашёл его раньше, чем
`src/pages`. Найдя оба каталога в разных местах, Next останавливает сборку.

Побочное следствие: при существующем `pages/` Next считает, что часть кода
может исполняться в Pages Router, и типизирует `useSearchParams` и `useParams`
как возможный `null`. В App Router `null` не бывает. Чтобы не расставлять
проверки по страницам, адрес читает один хук — `useUrlParams`
(`src/shared/lib/navigation`).

Исключения из «одной строки» — два файла, где сама маршрутизация и есть
содержание: `app/layout.tsx` (документ, шрифты, провайдеры) и `app/admin/page.tsx`
(переход с `/admin` на `/admin/pipeline`). Обработчики `app/api/[...path]/route.ts`
и `app/config.json/route.ts` объявляют настройки сегмента маршрута, которые Next
читает только из самого файла маршрута.

## Слой `app`

| Сегмент | Что лежит |
|---|---|
| `entrypoint` | `Providers`: кэш запросов TanStack Query и сессия пользователя |
| `styles` | `globals.css`: токены приложения и базовые правила документа |
| `api-routes` | `proxyApiRequest`: пересылка `/api/*` на `speech-ms` |

## Слой `pages`

Срез страницы держит всё, что нужно только этому экрану: состояние в адресе,
запросы, расчёты, блоки и их стили.

| Срез | Маршруты | Что внутри |
|---|---|---|
| `dashboard` | `/` | Обращения по темам во времени: `model/dashboard.ts` (состояние, шкала, итог словами), `model/chart.ts` (цвета тем), блоки графиков и плиток |
| `dialogs` | `/dialogs`, `/calls/[id]` | Поиск по расшифровкам: вкладки источника, строка поиска, фильтры, темы, выдача в шести состояниях |
| `quality` | `/quality` | Оценка по скрипту: блоки макета заказчика, список звонков, разбор звонка, файл сверки |
| `admin/pipeline`, `jobs`, `topics`, `projects`, `settings`, `reports`, `audit`, `users` | `/admin/*` | По экрану администрирования на срез; у каждого свои запросы в `api` |

`admin` — группа срезов, а не срез: общего кода в самой папке нет. Общее для
экранов администрирования лежит в виджете `admin-shell`.

Внутри `quality/model` расчёты разложены по смыслу: `state` (состояние и адрес),
`queries` (параметры запросов), `stages`, `objections`, `outcomes`, `trend`,
`weeks`, `operators`, `headline`, `checklist`, `review-file`.

## Слой `widgets`

| Срез | Кто использует | Что это |
|---|---|---|
| `call-panel` | `dialogs`, `quality` | Панель разговора: реквизиты, плеер с метками совпадений, транскрипт, классификация, оценка по скрипту |
| `section-tabs` | `dashboard`, `dialogs`, `quality` | Вкладки разделов; «Оценка качества» видна с правом `quality` |
| `admin-shell` | маршрут `/admin`, все `admin/*` | Рамка администрирования и её общие части: проверка права, вкладки, `Screen`, `AsyncTable`, `Banner`, `Field`, `Pill`, таблица стилей `adminStyles`, текст отказа, ключи кэша и изменение с перечитыванием журнала |

## Слой `features`

| Срез | Кто использует | Что это |
|---|---|---|
| `call-search` | `dashboard`, `dialogs`, `quality` | Поиск разговоров: состояние поиска и его запись в адрес (`model/search-state.ts`), запросы выдачи и счётов периода, карточка найденного разговора `ResultCard` |

Действия, которые нужны одному экрану, — выгрузка дашборда, файл сверки,
повтор задания — лежат в срезе своей страницы. В `features` они переедут,
когда понадобятся второму экрану.

## Слой `entities`

| Срез | Что это |
|---|---|
| `call` | Звонок: типы карточки и реплик, источники, сегменты и продукты с подписями, запрос карточки, справочники операторов и проектов, адрес записи, плеер записи `useRecordingPlayer` |
| `evaluation` | Оценка звонка по скрипту: типы, шкала балла, состояние этапа, текст отказа оценки, реплики-доказательства, запрос оценки |
| `classifier` | Классификатор обращений: дерево из плоского списка, путь одной строкой, выбор по уровням `ClassifierPicker` |
| `session` | Сессия пользователя: `SessionProvider`, `useSession`, права, вход, кука для аудио, `SessionGate` |
| `job` | Задание конвейера: этапы, состояния и полосы с подписями |

## Слой `shared`

| Сегмент | Что лежит |
|---|---|
| `api` | `request`, `ApiError`, `apiUrl`, сгенерированная схема контракта и тип `Schemas` |
| `config` | Конфигурация стенда из `/config.json`, её сборка из окружения, пояс показа `displayTimeZone` |
| `lib/date` | Сутки и периоды: начало суток в поясе, период по умолчанию, сдвиг границы, подписи |
| `lib/format` | Дата, длительность, счётные слова, проценты |
| `lib/highlight` | Разбор подсветки найденного в цитате |
| `lib/calendar` | Сетка месяца для календаря |
| `lib/download` | Скачивание файла с отказом словами |
| `lib/navigation` | `useUrlParams`: параметры адресной строки |
| `ui/analytics-kit` | Общий вид «Дашборда» и «Оценки качества»: токены макета заказчика, каркас страницы, карточка блока |
| `ui/day-picker` | Граница периода с календарём |

## Стили

Один компонент — один CSS-модуль рядом с ним. Общие для нескольких компонентов
среза классы лежат в `common.module.css` среза (в разборе звонка —
`review.module.css`).

Таблица стилей, общая для нескольких срезов, отдаётся через публичный API:

```ts
// src/shared/ui/analytics-kit/index.ts
export { default as kit } from './analytics-kit.module.css';
```

Токены макета заказчика объявлены на классе `kit.page`: всё внутри него
наследует цвета текста, акцент и шкалу оценки. Классы шкалы (`good`, `fair`,
`poor` и заливки) повторены в модулях тех блоков, которые красят ими свои
элементы: так цвет блока не зависит от того, в каком порядке сборка склеит
модули.

## Проверки

| Команда | Что проверяет |
|---|---|
| `pnpm typecheck` | Типы |
| `pnpm lint` | Biome: стиль и форматирование |
| `pnpm lint:fsd` | Steiger: направление импортов, импорты между срезами, обход публичного API, названия сегментов |
| `pnpm lint:docs` | `scripts/check-docs.mjs`: докстринг с описанием, `@param` и `@returns` у каждой функции |
| `pnpm lint:styles` | `scripts/check-styles.mjs`: обращения к несуществующим классам и классы без пользователей |
| `pnpm test` | Vitest: тесты рядом с кодом |
| `pnpm build` | Сборка Next |

`pnpm lint:styles` закрывает дыру, которой нет у TypeScript: опечатка в
`styles.titel` даёт `undefined` вместо класса, и элемент молча теряет вид.

## Как проверялся перенос 12.10.2026

Перенос не менял поведение и вид экранов. Это проверено тремя способами:

- **Код.** После раскладки по слоям каждое из 608 объявлений верхнего уровня
  исходного дерева сверено с новым без учёта комментариев: 591 совпало
  дословно, 17 изменены намеренно — страницы, рамка администрирования, ключи
  кэша и подмены модулей в тестах. Следующие шаги — разбор больших компонентов
  и общих таблиц стилей — намеренно изменили ещё 63 объявления; их проверяют
  тесты и снимки экранов.
- **Тесты.** Все 245 тестов исходного дерева проходят на новом; сами проверки
  не менялись, часть случаев переехала к коду, который они проверяют.
- **Экраны.** 40 снимков всех экранов на подставном API сняты до переноса и
  сравнены с новой сборкой попиксельно, с нулевым допуском: широкий и узкий
  экран, календарь, подсказка графика, панель разговора, разбор звонка, экраны
  без прав.

- **Действия.** Сценарий из 105 действий пользователя по всем экранам прогнан на
  сборке до переноса и на новой, на подставном API. На каждом шаге совпали
  адрес, запросы к API (177, вместе с телами изменений), текст страницы и
  состояние плеера: фильтры и вкладки, панель разговора с перемоткой и
  скоростью, разбор звонка, выгрузки с отказом, все изменения в
  администрировании, экраны без прав.

Проверки шли на подставном API. С настоящим бэкендом новая сборка не
запускалась; сквозные прогоны Playwright (`e2e/`) требуют поднятого стенда и
тоже не запускались.

## Что убрано как неиспользуемое

Решение владельца 12.10.2026: мёртвый код не держим — всё, что в новом
приложении не используется, удалено.

- **Раскрытие скрытого и маска.** Кнопка «Показать скрытое», её запрос, право
  `reveal_pii` и штриховка на месте `•••` в транскрипте: в `speech-backend`
  обезличивания нет, текст реплики один.
- **Этап `mask`.** Убран из фильтра заданий, переобработки и «попыток по
  этапам»: миграция бэкенда удалила такие задания и запретила их в базе.
  Подпись события журнала `pii.reveal` оставлена — старые записи журнала с ним
  остаются и должны читаться.
- **Выход и подпись пользователя.** `startLogout`, `getDisplayName` и
  `getDisplayInitials` были покрыты тестами, но ни один экран их не вызывал.
  Кнопки «Выйти» в интерфейсе нет и не было; понадобится — её надо писать, ручка
  `/api/v1/auth/logout` на бэкенде есть.
- **Блок `keycloak` в конфигурации.** Шесть переменных `SPEECH_KEYCLOAK_*`
  читались из окружения и отдавались в `/config.json`, но браузер их не
  использовал с тех пор, как вход переехал на сервер. Если они заданы в
  развёртывании, они просто не читаются.
- **`deploy/speech-edge.nginx.conf`.** Конфигурация nginx перед фронтом нигде
  не подключалась: `/api` пробрасывает сам фронт.
- **Мелочи.** Неиспользуемые константы, 16 псевдонимов типов, 14 переменных CSS
  и параметры, которые в приложении всегда принимали одно значение.

Схема `src/shared/api/schema.d.ts` перегенерирована из контракта 3.0.

После чистки экраны и действия сверены с состоянием до неё в условиях нового
бэкенда (без права раскрытия и без этапа `mask`): изменились только три экрана
администрирования — «Задания», «Настройки» и «Отчёт», где исчезли этап
«обезличивание» и слова о скрытых данных в расшифровке.
