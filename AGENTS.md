# Правила работы с speech-frontend

## Область работы

- Интерфейс речевой аналитики: «Дашборд», «Диалоги», «Оценка качества» и
  администрирование. Next.js 15 App Router, React 19, TypeScript strict.
- Код перенесён из `aisistent-speech` 12.10.2026 и разложен по Feature-Sliced
  Design. Исходную папку не читаем, не меняем и не используем для копирования.
- Бэкенд — `speech-backend`. Его исходники не импортируем: общий у проектов
  только контракт `openapi.speech.json`, из него порождается
  `src/shared/api/schema.d.ts`.
- Поведение и вид экранов при рефакторинге не меняем. Изменение поведения —
  отдельная задача со своим решением владельца.

## Архитектура: Feature-Sliced Design

Код в `src/` разложен по слоям. Слой импортирует только из слоёв ниже себя:

| Слой | Что лежит | Срезы сейчас |
|---|---|---|
| `app` | Запуск приложения: провайдеры, глобальные стили, обработчики `/api` | сегменты `entrypoint`, `styles`, `api-routes` |
| `pages` | Экран целиком и всё, что нужно только ему | `dashboard`, `dialogs`, `quality`, `admin/*` |
| `widgets` | Крупный самостоятельный блок, который стоит на нескольких экранах | `call-panel`, `section-tabs`, `admin-shell` |
| `features` | Действие пользователя, общее для нескольких экранов | `call-search` |
| `entities` | Понятие предметной области: данные, правила, запросы, малый вид | `call`, `evaluation`, `classifier`, `session`, `job` |
| `shared` | То, что не знает о предметной области | `api`, `config`, `lib/*`, `ui/*` |

Правила, которые нарушать нельзя:

- **Вниз, не вверх и не вбок.** Срез не импортирует из слоя выше и из соседнего
  среза своего слоя. Двум страницам нужно одно и то же — оно опускается в
  `widgets`, `features`, `entities` или `shared`.
- **Только через публичный API.** Чужой срез импортируется по его корню:
  `@/entities/call`, а не `@/entities/call/model/labels`. Наружу срез отдаёт
  то, что перечислено в его `index.ts`.
- **Внутри среза — относительные пути.** `../model/state`, а не
  `@/pages/quality/model/state`: свой `index.ts` срез сам не импортирует.
- **Сегменты названы по назначению:** `ui` — компоненты и их стили, `model` —
  типы, состояние и чистые функции, `api` — запросы к серверу, `lib` —
  вспомогательный код среза. Папок `components`, `hooks`, `utils`, `types` нет.
- **Сначала страница.** Новый код кладём в срез страницы. В нижний слой он
  переезжает, когда понадобился второму экрану, а не заранее.
- **`shared` не знает слов «звонок», «оценка», «оператор».** Понадобилось
  такое слово — это `entities`.

Next.js и FSD делят имена `app` и `pages`, поэтому:

- маршруты Next лежат в корневом `app/` и только отдают страницу:
  `export { QualityPage as default } from '@/pages/quality'`. Логики, состояния
  и разметки в них нет;
- корневой `pages/` — заглушка с `README.md`. Без неё Next принял бы слой
  `src/pages` за Pages Router и сборка упала бы. Не удалять и не наполнять;
- из-за заглушки Next типизирует `useSearchParams` и `useParams` как возможный
  `null`. Параметры адреса читаем через `useUrlParams` из
  `@/shared/lib/navigation`.

Что где лежит и почему — [docs/architecture.md](docs/architecture.md).

## Код

- Состояние экранов живёт в адресе. Разбор и сборка адреса — чистые функции в
  `model` с тестами рядом.
- Запросы — TanStack Query в сегменте `api` среза. Типы ответов берём из
  `Schemas` (`@/shared/api`), руками формы ответов не переписываем.
- Один компонент — один файл и один CSS-модуль рядом: `Calls.tsx` и
  `Calls.module.css`. Классы, общие для нескольких компонентов среза, — в
  `common.module.css` среза. Таблицу стилей другого среза берём через его
  публичный API: `kit` из `@/shared/ui/analytics-kit`, `adminStyles` из
  `@/widgets/admin-shell`.
- Тест лежит рядом с тем, что проверяет: `state.ts` и `state.test.ts`.
- Обезличивание в новый бэкенд не возвращается; оценка продаж применяется
  только к звонкам Телфина.

## Докстринги

У каждой функции есть докстринг на русском: что она делает, что принимает и
что возвращает.

- Первая строка — действие глаголом в настоящем времени: «Собирает…»,
  «Проверяет…». У компонента — что он показывает.
- Ниже, если это не очевидно из кода, — почему сделано так.
- `@param` — на каждый параметр. Свойства компонента — через точку:
  `@param props.callId`.
- `@returns` — что возвращается; у функции без результата тега нет.
- `@throws` — значимые ошибки.

```ts
/**
 * Находит реплику, которая звучит в заданный момент записи.
 *
 * Реплики идут по порядку начала; звучащая — последняя из тех, что уже начались.
 *
 * @param segments Реплики расшифровки по порядку.
 * @param position Позиция в записи, в секундах.
 * @returns Номер реплики (`seq`) или `-1`, если запись ещё не дошла до первой.
 */
export function activeSeq(segments: readonly Segment[], position: number): number {
```

Функцией считается объявление `function`, стрелочная функция или `useCallback`
в переменной и метод класса — на любом уровне вложенности, включая помощников
в тестах. Безымянные обработчики (колбэк `map`, обработчик события в разметке,
тело эффекта) докстринга не требуют: их объясняет функция, внутри которой они
стоят.

Докстринг описывает код, какой он есть. Историю правок в нём не ведём — она в
git.

## Проверки

После изменения кода запускаем всё и не ослабляем проверки ради зелёного
прогона:

```bash
pnpm typecheck      # типы
pnpm lint           # Biome: стиль и форматирование
pnpm lint:fsd       # Steiger: слои, срезы и публичные API
pnpm lint:docs      # докстринг у каждой функции
pnpm lint:styles    # классы в компонентах и CSS-модулях сходятся
pnpm test           # Vitest
pnpm build          # сборка Next
```

`pnpm check` запускает их подряд. Сквозные прогоны Playwright (`pnpm e2e`)
идут против поднятого стенда и в этот набор не входят.

Для изменений только в документации проверяем ссылки и согласованность с кодом.
Решения записываем в `docs/` и добавляем ссылку сюда.
